# TwitchManager 1.0.2 feature plan

## Release baseline

The `dev_1.0.2_beta` release baseline contains all existing changes consolidated from `uka`, the outbound-raid self-introduction fix from `uka_bug`, and the distributable TwitchManager logo.

The partial obs-websocket implementation inherited from `uka` is removed from the 1.0.2 baseline. It asked users to configure a host, port, password, and separate OBS Media Sources, which conflicts with the selected low-setup design. Removed obs-websocket settings are also stripped from saved settings and restored backups.

## Issue #34: one OBS audio source for every TwitchManager sound

### Product decision

Create a dedicated `TwitchManagerAudio.html` page and add it to OBS once as a **Browser Source**. Every TwitchManager notification sound is sent to that page and reaches the OBS Audio Mixer as one source. This is the only planned OBS route for 1.0.2; there is no obs-websocket fallback.

The installer should provide an `OBS_Audio_Source_URL.txt` next to the existing dock URL. Automatically creating the source would require privileged OBS control, so the user performs the one-time Browser Source registration.

Place a localized **OBSで通知音を使う方法 / OBS audio setup / OBS 通知音設定** explanation button next to the notification-sound settings. The explanation must cover:

1. Where to find or copy the Browser Source URL.
2. How to add it to OBS once.
3. How OBS mixer output and audio monitoring affect what the stream and broadcaster hear.
4. How to play a test sound and confirm that only one copy is heard.
5. Basic troubleshooting for an inactive source, muted mixer channel, or a source that was shut down while hidden.

### Required feasibility spike

1. Verify whether the installed dock and Browser Source can exchange playback requests reliably in supported OBS versions on Windows and macOS.
2. Prefer `BroadcastChannel` when both local browser contexts can communicate reliably.
3. If local-file context isolation makes that unreliable, use a minimal local relay or another same-install communication mechanism that does not require OBS credentials. Do not restore obs-websocket as a fallback.
4. Verify OBS relaunch, source visibility, duplicate-event prevention, rapid consecutive sounds, and Browser Source shutdown behavior.

### Internal design

- Route every notification through one sound-output interface instead of calling `Audio.play()` directly from event handlers.
- Backends are direct in-app preview/playback and the dedicated OBS Browser Source relay.
- A normal notification is sent to one active output path so it is not played twice.
- Individual raid, comment, channel-point, first-comment, and listener-arrival settings only choose enablement, sound assignment, and volume.
- Test playback uses the same routing path as live events.
- Never change OBS mixer or monitoring settings automatically.
- Do not store OBS connection credentials because this design does not use them.

### Acceptance criteria

- OBS can mix and record all TwitchManager sounds through one Browser Source.
- Setup requires no obs-websocket host, port, password, or per-notification OBS source selection.
- The notification-sound area contains a user-readable localized setup button.
- One notification produces one audible playback request.
- Direct playback remains usable when TwitchManager is used outside OBS.
- Windows and macOS installers include the Browser Source page and URL guide.

Suggested branch: `feature/1.0.2-audio-source`.

## Listener-arrival bonus sound

### Detection decision

Chat messages are not used as the arrival signal. Periodically call Twitch Helix **Get Chatters** and compare snapshots, allowing a configured listener to be detected while lurking without posting a message.

This requires the broadcaster or moderator user access token to include `moderator:read:chatters`. Twitch documents that the returned chatter list can be delayed, so the UI and help text must describe the feature as delayed presence detection rather than exact real-time entry/exit tracking.

IRC JOIN/PART is not the primary route: Twitch does not send membership events for rooms with more than 1,000 users and IRC delivery may be duplicated or out of order.

### Behavior

- A user can register one or more listeners by stable Twitch user ID and assign a sound to each entry.
- On startup or when tracking is enabled, take a baseline chatter snapshot without playing sounds for users already present.
- After the baseline, an absent-to-present transition for a registered listener triggers the assigned sound once during the current live stream.
- Leaving and returning during the same stream does not play the sound again.
- The once-per-stream record survives dock reloads and OBS restarts by storing the Twitch stream ID with the listener ID.
- A new Twitch stream ID makes the listener eligible again. Offline presence does not consume eligibility.
- Display names are presentation data only; matching uses Twitch user ID.

### Data and polling model

- Store versioned listener entries containing `userId`, last known login/display name, enabled state, and sound reference.
- Store the last played Twitch stream ID separately per listener.
- Fetch all Get Chatters pages, respect rate-limit headers, avoid overlapping polls, and back off after API errors.
- Keep the previous successful snapshot for transition detection. A failed or incomplete poll must not be treated as everyone leaving.
- Reuse the unified sound-output interface from issue #34.

### Acceptance criteria

- A configured listener can trigger without sending a chat message.
- A configured listener triggers exactly once in one stream, including after a dock reload.
- The listener can trigger again in the next stream.
- Multiple configured listeners are tracked independently.
- Baseline users, disabled entries, and deleted entries never play unexpectedly.
- Delayed Twitch presence data and missing permissions are explained clearly in the UI.
- Settings and status text are localized in Japanese, English, and Simplified Chinese.

Suggested branch: `feature/1.0.2-listener-arrival-sound`.
