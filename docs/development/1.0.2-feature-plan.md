# TwitchManager 1.0.2 feature plan

## Release baseline

The `dev_1.0.2_beta` release baseline contains all existing changes consolidated from `uka`, the outbound-raid self-introduction fix from `uka_bug`, and the distributable TwitchManager logo.

The consolidated `uka` changes already include an initial implementation of issue #34. It provides a global browser/obs-websocket playback switch, OBS connection fields, input discovery, and `TriggerMediaInputAction` playback. This implementation remains available as a compatibility fallback while the lower-setup design below is evaluated.

## Issue #34: one OBS audio source for every TwitchManager sound

### Preferred direction

Create a dedicated `TwitchManagerAudio.html` endpoint and add it to OBS once as a **Browser Source**. All TwitchManager notification audio is then played inside that page, so OBS receives it as one mixer input. This removes per-sound OBS Media Source selection and avoids asking users for an obs-websocket port or password.

The installer should provide an `OBS_Audio_Source_URL.txt` next to the existing dock URL. The remaining user action is adding that URL as one Browser Source. Automatically creating the source would itself require privileged OBS control such as authenticated obs-websocket, so a completely zero-step setup is not a safe baseline.

### Required feasibility spike

1. Verify whether an OBS Custom Browser Dock and Browser Source loading the installed local files can exchange messages reliably through `BroadcastChannel` in supported OBS versions on Windows and macOS.
2. Verify whether both contexts share the settings and Twitch authentication storage required by the audio page.
3. Verify restart, OBS relaunch, source visibility, duplicate-event, and browser-source shutdown behavior.
4. If cross-context relay is unreliable, keep the current obs-websocket implementation as the supported 1.0.2 route instead of shipping a fragile automatic mode.

### Internal design

- Route every notification through one sound-output interface instead of calling `Audio.play()` or obs-websocket directly from event handlers.
- Backends: current browser playback, current obs-websocket Media Source playback, and the proposed Browser Source relay.
- The selected backend is global. Individual raid, comment, channel-point, first-comment, and listener-arrival settings only choose enablement and sound assignment.
- One notification produces exactly one playback request. Tests and live events use the same routing path.
- Never change OBS monitoring settings automatically.
- Do not log obs-websocket passwords or Twitch access tokens. Keep password data out of backups by default.

### Acceptance criteria

- OBS can mix and record all TwitchManager sounds through one source.
- The preferred route needs no obs-websocket port, password, or per-notification OBS source selection.
- Browser playback and OBS playback are mutually exclusive for each notification.
- Existing browser playback remains usable outside OBS.
- The current obs-websocket route remains available until the Browser Source route is proven on Windows and macOS.

Suggested branch: `feature/1.0.2-audio-source`.

## Listener-arrival bonus sound

### Behavior

- A user can register one or more listeners by stable Twitch user ID and assign a sound to each entry.
- The first chat message from a registered listener during a live stream triggers the assigned sound once.
- Further messages from that listener during the same stream do not trigger it again.
- The once-per-stream record survives dock reloads and OBS restarts by storing the Twitch stream ID with the listener ID.
- A new Twitch stream ID makes the listener eligible again. Offline chat does not consume eligibility.
- Display names are presentation data only; matching uses Twitch user ID so login/display-name changes do not break the rule.

### Data model

Store versioned entries containing `userId`, the last known login/display name, enabled state, and a sound reference. Store the last played Twitch stream ID separately per user. Reuse the unified sound-output interface from issue #34 so this feature follows the same browser/OBS playback choice.

### Acceptance criteria

- A configured listener triggers exactly once in one stream, including after a dock reload.
- The listener can trigger again in the next stream.
- Multiple configured listeners are tracked independently.
- Disabled or deleted entries never play.
- Unknown, renamed, or unavailable custom sounds fail visibly without breaking chat handling.
- Settings and status text are localized in Japanese, English, and Simplified Chinese.

Suggested branch: `feature/1.0.2-listener-arrival-sound`.
